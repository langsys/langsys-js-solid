## Scope

Every one of the spec's 113 rule ids is rowed exactly once. This is a binding: its profile is derived over
`langsys-js-typescript`, so a rule the core owns is `delegated`, naming the core row, the core's current
grade, and an absence probe whose control fires against the core's source. A delegated row resolves to the
core's grade. Rules the binding meets with its own code are graded on its own tests; rules no code in the
stack implements yet are `not implemented`.

**Status** is one of `implemented`, `provisional`, `delegated`, `partial`, `not implemented`,
`held (strip ruling)`, `waived`, `n/a (profile: <p>)` or `n/a (architecture: <reason>)`. **Tier** is `live`,
`contract` or `mock` where the property depends on what the API answers; in-process behaviour, meta-rules,
identity vectors and artifact inspection with a positive control are `n/a (pure)`; `delegated`,
`not implemented` and `n/a` rows take `-`.

## How the binding forwards the core

`LangsysApp` is the core singleton behind a Proxy. Methods are bound to the core and cached per property, so
`const { refresh } = LangsysApp` works and `LangsysApp.refresh === LangsysApp.refresh`. Accessors and state
pass through by reference, so `LangsysApp.t` is the core's own `t`, whose fresh identity per catalog change is
what every `useT()` consumer re-renders on. Only `init` and `setWriteGrant` are overridden, to accept Solid
shapes. An enumerated wrapper would silently omit public methods the core adds later; forwarding exposes them.
TypeScript's `private` is erased at runtime, so core-private members are forwarded too; the exported type
excludes them.

Capability (`useWriteEnabled`) reads `undefined` until mount, so the first client render agrees with what the
server rendered. The raw `writeEnabled` signal is not re-exported, since reading it synchronously would seed
a value the server never rendered.

## The bench

The binding is tested against the core's local build through `npm link`, never the registry: the published

## Gaps, ranked by cost

1. **SRV-1, SRV-2 — server renders serve the base language, from a process-global catalog.** Crawlers index
   the base language under localised URLs, and concurrent visitors in different locales can be served each
   other's language. Search visibility, and correctness under load.
2. **SRV-4 — no proven hydration hand-off.** Nothing seeds the catalog before hydration, and the client hosts
   are untested against the server markup. A page served in one language may re-render in another.
3. **SNAP-2 — no snapshot loader.** A first render or an offline session has no translations until the
   catalog fetch returns. Not implemented in the core either.
4. **MIG-1..8 — no migrate mode.** An app moving from key-based i18n cannot adopt Langsys incrementally. Not
   implemented in the core either.
5. **SRV-5 — no server-side child capture.** Blocked on the open decision on where it lives.
6. **CI installs the registry core.** `^0.6.5` resolves the published build, which lacks the surface this
   binding uses, so CI fails the precondition until the core publishes and the range follows it.
7. **Delegated rows resolving to `partial`.** REG-10, TOK-6, MARK-2 and MARK-3 carry the core's gaps.
